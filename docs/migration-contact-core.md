# Migration Contact Core

La base locale reste la source de travail. Avant tout import ou déploiement, sauvegarder séparément la base et les médias (`public/storage` pour les fichiers publics et `storage/app/private` pour les originaux, ainsi que tout autre chemin configuré), puis vérifier les chemins et les liens publics. L'import de la base du site doit être effectué sur une copie dédiée et ne doit pas écraser les médias existants. Les demandes de production ne sont pas une contrainte de conservation selon les instructions du propriétaire.

Pour chaque `contact_submissions`, la migration crée une demande et enregistre une correspondance unique dans `legacy_contact_inquiry_mappings`. Elle recopie les coordonnées, le sujet, le message et les dates originales ; le statut devient `handled` si `handled_at` existe, sinon `to_handle` si `read_at` existe, sinon `new`. Le contact est résolu par le modèle Core. Les livraisons existantes sont rattachées via `inquiry_id` sans modifier leur payload chiffré, leurs tentatives, leur statut ni leur clé. Les livraisons nouvelles utilisent une clé distincte `atelierivoincidit:inquiry:<id>`. Les tables et les lignes historiques restent en place. Les insertions et les correspondances sont transactionnelles pour permettre une reprise sans doublons.

Le schéma Core est fourni par les migrations du package. Vérifier les comptages et la correspondance des champs sur une copie avant toute bascule. Vérifier également les permissions, les e-mails, les médias et la reprise des livraisons. La migration ne déclenche aucun envoi historique.
